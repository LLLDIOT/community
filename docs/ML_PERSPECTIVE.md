# 从机器学习视角解析社团招新系统

> 本文回答一个问题：**这套系统的技术实现，放在机器学习的框架里应该怎么理解？**
>
> 结论会让人有点意外，但先说清楚比事后被问穿要好。

---

## 一、结论先行：系统里没有任何机器学习

先把话说直：**当前系统不含任何 ML 组件**。没有训练、没有模型权重、没有推理服务，也没有引入 TensorFlow / PyTorch / 向量库。

可以这样验证：

```bash
# 依赖里只有三个包，没有任何 ML 框架
cat server/package.json | grep -A5 dependencies
#   better-sqlite3 / express / multer

# 全仓库搜不到任何模型、权重、向量
grep -rniE "tensorflow|pytorch|onnx|embedding|model\.(pt|bin|onnx)|sklearn" server/src web/src
#   （无匹配）
```

那系统里被叫做"**智能匹配**"的东西是什么？见 `server/src/services/matchService.js`：

```js
const score = Math.round((hitSkills.length / requiredSkills.length) * 100);
```

翻译成一句话：**数一下简历上写的技能词，有几个和岗位要求里的词完全一样，做个除法。** 这是字符串集合求交集，是确定性的规则运算。

**为什么必须先澄清这一点**：如果对外把它包装成"AI 驱动的智能匹配"，在答辩或评审时只要问一句"你的模型是什么、训练集多大、指标多少"，就答不上来。反过来，把它的**真实数学本质**讲清楚，反而能体现对问题的理解深度——这正是本文要做的事。

---

## 二、把现有模块放进 ML 的概念坐标系

虽然没有 ML，但这套系统**在结构上恰好是若干 ML 系统的退化形式**。逐一看：

### 2.1 技能匹配 = 二值稀疏向量上的非对称重叠度

设技能词表 $V$（所有出现过的技能标签的并集）。把一份简历 $r$ 和一个岗位 $p$ 都编码成**二值向量**：

$$
\mathbf{x}^{(r)}_i = \begin{cases} 1 & \text{若技能 } v_i \text{ 出现在简历中} \\ 0 & \text{否则} \end{cases}
\qquad
\mathbf{x}^{(p)}_i = \begin{cases} 1 & \text{若技能 } v_i \text{ 在岗位期望中} \\ 0 & \text{否则} \end{cases}
$$

当前实现的打分是：

$$
\text{score}(r,p) = \frac{\sum_i x^{(r)}_i \cdot x^{(p)}_i}{\sum_i x^{(p)}_i} = \frac{|\mathbf{x}^{(r)} \cap \mathbf{x}^{(p)}|}{|\mathbf{x}^{(p)}|}
$$

这在 ML / IR（信息检索）里有个标准名字：**非对称的二值重叠系数**。它和几个经典度量的关系是：

| 度量 | 公式 | 与当前实现的关系 |
|---|---|---|
| **余弦相似度** | $\dfrac{\mathbf{x}^{(r)}\cdot\mathbf{x}^{(p)}}{\|\mathbf{x}^{(r)}\|\,\|\mathbf{x}^{(p)}\|}$ | 分母多了 $\|\mathbf{x}^{(r)}\|$，变成对称 |
| **Jaccard** | $\dfrac{|\cap|}{|\cup|}$ | 惩罚"简历上乱七八糟写了一堆技能" |
| **当前实现** | $\dfrac{|\cap|}{|\mathbf{x}^{(p)}|}$ | **只惩罚漏掉的技能，不惩罚堆砌** |

**这个设计选择的后果**：一份简历如果把网上能找到的所有技能标签都填上（Vue、Python、设计、文案、篮球……），它的匹配度会**单调上升**而没有任何代价。这是一个可被利用的弱点——技术上叫 **关键词堆砌攻击（keyword stuffing）**。用 Jaccard 或余弦就能缓解（分母会随简历技能数增长）。

### 2.2 排序函数 = 手工构造的 scoring function

`recommendPositionsForResume()` 里的排序：

```js
.sort((a, b) =>
  b.score - a.score ||                                            // ① 匹配度
  (b.status === 'open') - (a.status === 'open') ||                 // ② 招新中的优先
  a.filledCount / Math.max(1, a.headcount) - b.filledCount / ...   // ③ 招满率低的优先
)
```

这就是一个**人工设计特征 + 人工设定权重顺序**的排序器。在 ML 里，这正是 **Learning-to-Rank（LTR）**要学习的东西：把「① ② ③ 三个特征的组合方式」从手写改成用数据学出来，比如 LambdaMART 或 XGBoost-Rank。

**换句话说：这个排序函数就是 LTR 的"基线模型"，只是权重是拍脑袋定的。**

### 2.3 面试决策 = 一个正在生产训练数据的人工标注流程

这是全系统**与 ML 关系最近**的部分。

`decision` 字段（录用 / 候补 / 调剂 / 淘汰）是社团干部对每个候选人的**人工判断**。从 ML 的角度看：

$$
\text{样本} = (\underbrace{\text{skills, grade, major, matchScore, 面试评分}}_{\text{特征 } \mathbf{x}},\; \underbrace{\text{decision}}_{\text{标签 } y})
$$

**系统已经把特征和标签分开存了**，而且：

| 要素 | 系统里对应什么 | 状态 |
|---|---|---|
| 特征 | `resume.skills` / `resume.grade` / `resume.major` / `matchScore` / `application.score` | ✅ 已有 |
| 标签 | `application.decision` | ✅ 已有字段，**但数据为空** |
| 时间戳 | `created_at` / `decided_at` | ✅ 已有（可做时序切分，防泄漏） |
| 决策人 | `decided_by` | ✅ 已有（可做标注者一致性分析） |

**这是一个被设计成"能长出训练集"的结构**——虽然此刻一条标注都没有。这一点在第 4 节会用真实数字量化。

### 2.4 数据看板 = 描述性统计，也是未来的模型监控

看板里那些漏斗、分布、趋势，在 ML 工程里的对应物是：

- **EDA（探索性数据分析）**：上线前看数据长什么样
- **模型监控**：上线后盯 `feature drift`（技能分布变了）和 `label drift`（录取率变了）

`statusCounts` / `decisionCounts` 这两个聚合，天然就是**标签分布监控**的基本盘。

### 2.5 招新广场 = 曝光日志（可惜没记录）

推荐系统需要知道"**模型推荐了什么、用户看没看、点没点**"，这叫 **impression / click 日志**。

- 招新广场展示了所有社团 → 这是**曝光**
- 学生点了哪个社团卡 → 这是 **click**

**但系统没有记录这些**（没有任何埋点表）。这意味着：即使将来想训一个"该推荐哪个社团给学生"的 CTR 模型，也**没有训练数据**。这是当前架构在 ML 层面最实质的缺口。

### 2.6 权限体系 = 数据质量治理

`owner / interviewer / viewer` 三个角色，从 ML 角度看不是算法问题，而是**标注质量**问题：

- 谁有资格标注（`application:decide`）= 标注者资质
- `decided_by` = 标注溯源
- 观察员只读 = 防止污染训练数据

**小团队里标注一致性极差**（同一个候选人，两个面试官可能一个录用一个淘汰），这会直接变成**标签噪声**，是后面 LTR 最大的障碍之一。

## 三、实测：当前数据集上，三种相似度差多少

光讲公式没用，用系统里的**真实数据**跑一遍（`server/scripts/analyze-matching.mjs`）：

```bash
cd server && node scripts/analyze-matching.mjs
```

### 3.1 语料现状

```
简历 4 份，岗位 3 个

技能        岗位df   简历df   IDF
沟通          1        1      1.693
海报          1        1      1.693
活动组织       1        1      1.693
排版          1        0      1.693
设计          1        1      1.693
文案          1        1      1.693
css          1        0      1.693
html         1        0      1.693
javascript   1        0      1.693
vue          1        1      1.693
```

**关键观察**：每个技能的 `df`（文档频率）都是 1——因为一共只有 3 个岗位，每个技能只被一个岗位要求。

后果：**IDF 全部相同（1.693），加权后比例不变**。也就是说在这个数据规模上，IDF 加权**毫无作用**。

> 这本身就是一个 ML 结论：**IDF 这类统计量在小语料上退化为常数**。它需要足够大的文档集合才有区分度。

### 3.2 三种打分对比

| 简历 | 岗位 | 精确（现状） | IDF 加权 | 余弦 | 命中技能 |
|---|---|---|---|---|---|
| 王小明 | 前端开发干事 | 25 | 25 | 29 | vue |
| 赵小红 | 活动策划干事 | 100 | 100 | 100 | 活动组织 / 沟通 / 文案 |
| 孙小美 | 宣传部干事 | 67 | 67 | 67 | 设计 / 海报 |

- 赵小红那份是 3 个技能全中，三种度量都给 100（此时它们数学上等价）
- 王小明只中 1/4，余弦 29% 略高于精确 25%（余弦会考虑简历本身的技能数）
- **排序结果完全一致**——没有出现 top1 被换掉的情况

### 3.3 想做 Learning-to-Rank 的话，样本够吗

```
样本总数 n = 3
已有明确结论（可当标签） = 0    其中 录用=0 淘汰=0
有年级特征 = 3   有技能特征 = 3   有人工评分 = 1
```

**标注样本 0 条。** 这不是"少"，是"没有"。

排序模型的经验门槛大致是 $10^3 \sim 10^5$ 量级的有标样本。当前差距是**三个数量级以上**。

## 四、如果要真正引入 ML：一条按投入产出排序的路线

下面每一级都写清楚"前置条件"和"代价"，而不是只列名词。

### L0 —— 现状：精确字符串匹配

- **输入**：逗号分隔的技能标签
- **方法**：集合求交
- **优点**：零成本、可解释、结果可复现（同一输入永远同一输出）
- **缺点**：同义词失效（`Vue` ≠ `vue3`）、无权重（`沟通` 和 `PyTorch` 等价）、可被堆砌
- **代码位置**：`matchService.js` → `matchSkills()`

### L1 —— TF-IDF / BM25 加权（**收益/成本比最高的一级**）

- **解决**：稀有技能权重大、常见技能权重小
- **前置条件**：技能语料 ≥ 几十个岗位，IDF 才有区分度（**当前 3 个岗位不够**）
- **改动量**：只改 `matchSkills()` 内部约 20 行，其余接口不变
- **代价**：极低（纯统计，无需标注、无需训练）
- **实测提醒**：本系统当前数据下 IDF 是常数，**现在做等于没做**

### L2 —— 文本嵌入 + 向量检索（质的飞跃）

- **解决**：语义泛化。`Vue3` ↔ `前端框架` ↔ `组件化` 能算相似；`PS` ↔ `Photoshop`
- **方法**：
  1. 用中文/多语嵌入模型（如 BGE 系列）把「简历正文」和「岗位要求」各编码成 768 维向量
  2. 余弦相似度替代字符串匹配
  3. 岗位数量上来后用 HNSW / IVF 做近似最近邻
- **前置条件**：一个嵌入服务（本地跑小模型，或调 API）+ 向量存储
- **改动量**：新增 embedding 层；`matchService` 改为调用它；需要缓存（简历只在创建时编码一次）
- **代价**：中。新增依赖、首次编码延迟、要处理模型版本升级导致向量失效
- **收益**：这一级才是"看起来像 AI"的效果来源

### L3 —— Learning-to-Rank（需要标注）

- **解决**：把 L2.2 里那个手写的排序函数换成学出来的
- **特征**：语义匹配度、年级、专业相关度、面试评分、历史同类岗位录取率
- **模型**：LambdaMART / XGBoost-Rank（这类模型在小样本上比深度模型稳）
- **标签**：`application.decision`
- **前置条件（硬门槛）**：
  - 有标样本 $\gtrsim 10^3$（当前 **0**）
  - 标注一致性可接受（需要至少 2 人独立标注一批做 Kappa 检验）
- **代价**：高。要防过拟合、要做时序切分、要保留可解释性
- **当前判断**：**不具备条件**

### L4 —— 跨社团全局模型 / 联邦学习

- 把多个社团的决策数据合起来训练，缓解单社团样本不足
- 需要处理：社团异质性（美术社和计协的"优秀"定义不同）、隐私（学生简历不能随意跨社团共享）
- 现实约束：**在当前部署形态下不具备数据合规基础**，不建议考虑

### 路线小结

| 级别 | 方法 | 需要标注 | 当前可行性 |
|---|---|---|---|
| L0 | 精确匹配 | 否 | ✅ 已实现 |
| L1 | TF-IDF / BM25 | 否 | ⚠️ 语料太小，效果为零 |
| L2 | 文本嵌入 | 否 | 🔶 可行，需新增服务 |
| L3 | Learning-to-Rank | **是** | ❌ 样本 0，不可行 |
| L4 | 跨社团 / 联邦 | 是 | ❌ 合规与样本均不满足 |

## 五、为什么"现在上 ML"是个错误决定

这一节是本文最该被认真读的部分。五个理由，按严重程度排序：

### 5.1 样本量差三个数量级

一个社团一季收到几十份投递，其中最终有明确结论的可能 10~30 条。而 LTR 通常要 $10^3$ 以上。

**在 30 条样本上训一个排序模型，模型会记住这 30 个人，而不是学到"什么样的人适合这个社团"。** 上线后面对新候选人，表现不会比"数技能个数"更好——而且更不可解释。

### 5.2 标签不是"真实偏好"，而是"名额约束下的妥协"

这是**结构性偏差**：岗位只要 2 人，第 3 名优秀的候选人也会被标成"淘汰"。

也就是说 $y = \text{淘汰}$ 并不代表"这个候选人不合适"，而可能是"这个候选人排第 3"。

**用这种标签训二分类模型，学到的是"谁排进了前 N"，而不是"谁优秀"**——这跟业务目标（找合适的人）不是一回事。要正确处理得用 **listwise LTR**（对同一岗位下的候选人整体排序），而不是逐条分类。

### 5.3 选择偏差（selection bias）

只有"被看到并被决策"的候选人产生标签。如果某个岗位的简历筛选一直很粗糙，那部分数据就是噪声；而没被投递的岗位完全没有数据。

**这是推荐系统的经典困境**，需要 **反事实评估 / off-policy evaluation** 才能正确处理，工程量远超本项目。

### 5.4 可解释性：招新必须能解释"为什么"

社团招新涉及学生利益，面试官需要能回答"为什么录取他而不是我"。

- 规则引擎：`命中 vue / 沟通，缺 html / css` —— 直接可解释
- 深度模型：一个 0.73 的分数 —— 说不清

要用 ML 就必须配 SHAP / LIME 之类的解释层，又增加一层成本和不确定性。

### 5.5 边际收益远小于运维成本

现在的规则引擎**准确率已经够用**——因为大部分岗位的技能要求本来就很明确（前端岗要 Vue，宣传岗要设计）。

引入嵌入模型带来的增量，在**投递量只有几十份**的场景下，人工翻一遍简历只要几分钟。**用 ML 省下的时间，抵不上维护它的时间。**

## 六、值得肯定的地方：这套设计暗合了 ML 工程实践

抛开"没有模型"这一点，系统在结构上有五处是**符合 ML 工程直觉**的：

### 6.1 特征与标签分层，而不是混进状态机

`status`（流程走到哪）与 `decision`（面试结论）是两个字段。**这在 ML 数据工程里是正确做法**：

- 如果为了存"候补 1 号"而给 `status` 加一个值，`status` 就同时承担了"流程状态"和"排序标签"两种语义
- 一旦语义混了，**标签就再也干净不回来了**——这是很多真实 ML 项目返工的原因

当初把两者拆开，是个正确的决定。

### 6.2 确定性基线（deterministic baseline）

`matchSkills` 无随机性、无外部调用、结果可复算。这意味着：

- 任何人可以独立复现同一个分数
- 将来引入模型时，**有一个稳定的对照基线**可以衡量"到底提升了多少"

**没有基线的 ML 项目无法证明自己有用。**

### 6.3 数据契约与版本化

- 迁移脚本 `001~004` 版本化演进，`PRAGMA user_version` 记录已执行到哪
- 字段白名单（`pickClubFields` / `pickResumeFields`）防止任意字段写入

对应 ML 工程里的 **feature schema 管理**：特征定义要可追溯、可回滚。

### 6.4 可观测性：指标天然对齐模型监控

看板上的 `statusCounts`（标签分布）、`decisionCounts`（结论分布）、`trend`（时序趋势），
换成 ML 的说法就是 **label distribution monitoring**——模型上线后最需要盯的东西。

### 6.5 Human-in-the-loop（人工兜底）

匹配分只是**建议**，所有实际决策（录用/淘汰）都要人点。这是负责任的做法：

- 算法给候选排序，人来拍板
- 系统从不自动淘汰任何人

对于涉及学生利益的高风险场景，**这是正确的设计**，而不是"技术不够"。

## 七、如果要往前走，第一步该做什么

**不是引入模型，而是把标注积起来。** 具体三件事，按顺序：

### 第一步：把 `decision` 真正用起来（当前为 0 条）

系统已经有字段、有接口、有界面，只是没人填。**每一季招新都认真标完**，一季就能积累几十条。

### 第二步：加曝光埋点（当前完全缺失）

学生端"看了哪些社团、点了哪个岗位"没有记录。这是将来做推荐**唯一**的数据来源。

最小实现：一张 `impression` 表（`who / what / when / action`），学生端打开社团详情时写一条。

### 第三步：积累到 $\gtrsim 300$ 条有标样本后，再考虑 L2（嵌入）

为什么先 L2 而不是 L3：
- L2 **不需要标注**，只要数据量够就能上，收益立竿见影（语义泛化）
- L3 需要标注，且要处理 5.2~5.4 的三个统计陷阱

---

## 八、一句话总结

> **这套系统现在不是机器学习系统，而是一个"被设计成将来能长出机器学习系统"的规则引擎。**
>
> 它的技能匹配本质是二值稀疏向量上的非对称重叠度（一个退化到极致的相似度度量）；
> 它的面试决策流程正在生产训练数据，但目前样本为 0；
> 它的架构分层（状态 vs 结论、确定性基线、可观测性、人工兜底）恰好符合 ML 工程的基本纪律。
>
> **在只有几十份投递、零条标注的现实下，规则引擎不是"技术落后"，而是"正确的工程判断"。**
