# 机器学习模型讲解

本文说明系统内使用的句向量模型：它是什么、结构如何、怎样产生向量、实测表现怎样，以及一处必须知晓的能力缺陷。文中数值均由 `server/scripts/explain-model.mjs` 在本地实测得到。

## 一、模型标识与来源

| 项目 | 内容 |
|---|---|
| 完整标识 | `Xenova/bge-small-zh-v1.5` |
| 原始模型 | `bge-small-zh-v1.5`，由北京智源人工智能研究院（BAAI）发布 |
| 格式转换 | `Xenova` 将 PyTorch 权重转换为 ONNX 格式 |
| 模型类型 | 句向量（sentence embedding）模型 |
| 用途 | 输入一段文字，输出一个固定长度向量 |

该模型属于编码器（encoder）类模型，不生成文本，只输出向量。系统用它把「简历文本」与「岗位文本」分别编码，再比较两个向量的相似程度。

## 二、结构参数

参数取自模型目录下的 `config.json`。

| 参数 | 取值 | 含义 |
|---|---|---|
| `architectures` | `BertModel` | 采用 BERT 编码器结构 |
| `hidden_size` | 512 | 输出向量维度 |
| `num_hidden_layers` | 4 | Transformer 层数 |
| `num_attention_heads` | 8 | 每层注意力头数 |
| `intermediate_size` | 2048 | 前馈网络中间层宽度 |
| `vocab_size` | 21128 | 词表条目数 |
| `max_position_embeddings` | 512 | 最长输入 token 数 |

按上述参数估算参数量：

```
词嵌入矩阵    21128 × 512                  ≈ 1082 万
每层编码器    4 × 512² + 2 × 512 × 2048    ≈  315 万
4 层合计                                  ≈ 1260 万
────────────────────────────────────────────────────
总计                                      ≈ 2340 万
```

作为参照，GPT-3 的参数量为 1750 亿，约为本模型的 7500 倍。对于「判断两段中文是否语义接近」这一任务，2340 万参数量已足够。

词表 21128 对应中文 BERT 系列的字符级词表：中文按单字切分。原因是中文词语组合数量近似无限，字符级覆盖更稳定。

## 三、磁盘占用与运行时

| 文件 | 体积 |
|---|---|
| `onnx/model_quantized.onnx` | 22.9 MB |
| `tokenizer.json` | 428.8 KB |
| 合计 | 23.32 MB |

模型以 int8 量化形式分发。量化把 32 位浮点权重压缩为 8 位整数，体积约为未量化版本的八分之一（未量化约 90 MB），代价是轻微的数值精度损失。

运行时为 ONNX Runtime，在 CPU 上单线程推理，不需要 GPU。

模型文件存放在 `server/data/models/` 下，通过环境变量 `HF_MIRROR`（默认 `https://hf-mirror.com`）获取。首次使用需下载，之后直接读取本地文件。实测本地加载耗时约 0.09 秒。

## 四、工作流程

### 4.1 分词

模型接收的是整数 token 序列，不接收字符串。分词由 `tokenizer.json` 定义的词表完成。

示例一：

```
原文：我是计算机协会的前端开发干事，负责页面开发
长度：23 个 token（含首尾特殊符）
切分：我 | 是 | 计 | 算 | 机 | 协 | 会 | 的 | 前 | 端 | 开 | 发 | 干 | 事 | …
```

示例二：

```
原文：精通 Vue 与 Node.js
长度：9 个 token
切分：精 | 通 | [UNK] | 与 | [UNK] | . | js
```

第二个示例中的 `[UNK]` 表示词表未收录该词条，具体影响见第六节。

### 4.2 编码

每个 token 经过 4 层 Transformer，逐层通过自注意力交换上下文信息。因此同一个字在不同上下文中会得到不同向量。

### 4.3 池化

模型对每个 token 位置都输出一个 512 维向量，需要合并为单一句向量。本实现采用 **CLS 池化**：取首个特殊符 `[CLS]` 位置的输出。

选择依据：BGE 系列模型在训练阶段以 `[CLS]` 位置的输出作为句向量参与对比学习目标。改用均值池化等其他方式，等同于取用未经训练的位置，效果会下降。

### 4.4 归一化

输出向量经归一化，欧几里得范数为 1：

```
维度     512
前 6 维  [-0.0177, -0.0130, 0.0718, -0.0526, -0.0015, -0.0664]
范数     1.000000
类型     float32（512 × 4 = 2048 字节）
```

归一化后余弦相似度等于点积，省去两次平方根运算与一次除法。

## 五、实测行为

### 5.1 相似度分布

| 余弦 | 类别 | 文本对 |
|---|---|---|
| 0.3942 | 无关 | 「精通 Vue 与 Node.js」与「会打篮球，参加过校队」 |
| 0.4951 | 无关 | 「喜欢摄影，擅长海报设计」与「会打篮球，参加过校队」 |
| 0.5102 | 相关但措辞不同 | 「前端开发」与「Vue3 页面实现与组件封装」 |
| 0.5440 | 同义表述 | 「海报设计」与「视觉传达与排版」 |
| 0.6109 | 同义表述 | 「活动策划」与「组织线下活动、协调场地」 |
| 0.6203 | 相关 | 「精通 Vue 与 Node.js」与「熟悉 Vue3 框架」 |
| 0.8462 | 同义表述 | 「文案」与「文案写作」 |

无关文本对的余弦下界约为 0.39，相关文本对的上界约为 0.85。取值区间明显窄于理论区间 [-1, 1]，因此系统对余弦做了线性标定（区间 [0.46, 0.75]），标定方法与依据见 `ML_TECHNICAL.md` 第 6 章。

### 5.2 输入长度上限与截断

```
长文本 1920 字 → 1922 个 token（截断前）
截断到 512    → 512 个 token
```

超出 512 token 的部分被直接丢弃，不参与计算。因此系统在构造文本时把「技能标签」放在「简历正文」之前，保证简历正文被截断时技能信息仍然完整。

### 5.3 编码性能

| 方式 | 耗时 |
|---|---|
| 逐条编码 | 3.6 ms/条 |
| 批量 20 条 | 20 ms（1.0 ms/条） |

批量编码显著快于逐条编码，因此缓存未命中的文本会集中成批送模型，而不是逐条调用。

## 六、已知缺陷：英文技术词失效

实测发现，该模型的词表不含英文技术名词，此类词条全部被切分为同一个 `[UNK]` token。测试结果：

| 词条 | 切分结果 | 是否含 `[UNK]` |
|---|---|---|
| Vue | `[UNK]` | 是 |
| React | `[UNK]` | 是 |
| Node.js | `[UNK]` `\|` `.` `\|` `js` | 是 |
| JavaScript | `[UNK]` | 是 |
| HTML | `[UNK]` | 是 |
| CSS | `[UNK]` | 是 |
| Python | `[UNK]` | 是 |
| PyTorch | `[UNK]` | 是 |
| Photoshop | `[UNK]` | 是 |
| Figma | `[UNK]` | 是 |
| UI设计 | `[UNK]` `\|` `设` `\|` `计` | 是 |

由于不同英文词条被映射为同一个 token，模型无法区分它们的语义。实测余弦值：

| 文本对 | 余弦 |
|---|---|
| 「Vue」与「React」 | 1.0000 |
| 「Vue」与「Python」 | 1.0000 |
| 「Vue」与「Photoshop」 | 1.0000 |
| 「精通Vue开发」与「精通React开发」 | 1.0000 |
| 「我会Vue」与「我会React」 | 1.0000 |

两组文本的 token 序列完全一致，因此输出向量完全一致，余弦为 1。

对比之下，中文概念的区分能力正常：「文案」与「文案写作」为 0.8462，「活动策划」与「组织线下活动、协调场地」为 0.6109。

该缺陷对本系统的影响：

1. 语义路径无法区分英文技术栈，「会 Vue」与「会 React」在语义层面等价。
2. 语义路径对中文概念有效，对英文技术词无效。
3. 因此技能命中率（字面比对）不是语义路径的补充手段，而是当前唯一能区分英文技能名称的路径。

这与系统采用「语义 0.6 + 标签 0.4」的融合权重直接相关：若权重偏向语义（例如 0.9 / 0.1），技术类社团的候选人在语义层面将难以区分。

## 七、选型依据

| 候选方案 | 取舍 |
|---|---|
| bge-small-zh-v1.5（当前） | 体积 23 MB，CPU 上 1~4 ms/条，中文效果好，可完全离线 |
| bge-large-zh | 体积约 1.3 GB，CPU 推理慢约一个数量级，收益不明显 |
| 多语言模型（bge-m3、paraphrase-multilingual-MiniLM） | 能正确处理英文技术词，但体积与耗时增加，中文表现略有下降 |
| 云端 Embedding 接口 | 按调用量计费、依赖网络、有请求延迟，且学生简历会离开本机 |

选择小模型的主要原因是可完全本地运行：不依赖网络、不产生调用费用、简历数据不出本机。

## 八、局限清单

| 局限 | 说明 |
|---|---|
| 英文技术词失效 | 全部映射为 `[UNK]`，语义层面无法区分 |
| 输入长度上限 | 512 token，超出部分丢弃 |
| 取值区间被压缩 | 余弦集中在 0.4~0.85，必须做线性标定 |
| 短文本表现较弱 | 仅有数个词时，向量偏向通用语义，区分力下降 |
| 无领域微调 | 使用通用中文语料训练，未在招新场景微调 |
| 标定参数不可移植 | [0.46, 0.75] 仅对该模型与当前数据成立，换模型需重新确定 |

## 九、改进方向

针对第六节的缺陷，有两种可选方案。

### 9.1 更换多语言模型

改用能正确切分英文的模型，例如 `bge-m3` 或 `paraphrase-multilingual-MiniLM-L12-v2`。

- 优点：从根本解决英文技术词的区分问题
- 代价：模型体积与推理耗时增加；余弦分布改变，需重新标定 `ML_CALIB_MIN` / `ML_CALIB_MAX`；需重跑 `verify-calibration.mjs` 确认分布

### 9.2 增加术语映射层

在编码前把英文技术词替换为带中文说明的形式，例如 `Vue` 替换为 `Vue 前端框架`，`PyTorch` 替换为 `PyTorch 深度学习框架`。

- 优点：不改模型，改动范围小，可保留现有标定参数
- 代价：需要维护一份术语映射表，且映射表覆盖面决定改进上限

两种方案均未实施。当前依靠技能命中率承担英文技能的区分职责。

## 十、验证方式

以下命令可复现本文全部数值：

```bash
cd server

# 结构参数、分词、向量、相似度基线、截断、编码耗时
node scripts/explain-model.mjs

# 模型基本信息与单条编码耗时
node scripts/probe-embedding.mjs

# 余弦→标定分→综合分的完整对照表与分布诊断
node scripts/verify-calibration.mjs
```

说明：`explain-model.mjs` 与 `probe-embedding.mjs` 直接调用模型，不依赖数据库；`verify-calibration.mjs` 读取数据库中的简历与岗位。
